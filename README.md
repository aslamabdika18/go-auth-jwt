# Go Auth JWT

Authentication and authorization REST API built with Go, Gin, PostgreSQL, and pgx.

It provides session-based JWT authentication (short-lived access token + rotating refresh token, both in HttpOnly cookies), user management, and a database-driven RBAC system (roles and permissions). A small Vite-based frontend is included for testing every endpoint from the browser.

## Features

- User registration with request validation and bcrypt password hashing
- Login with server-side **sessions** (each login creates a session that can be revoked)
- Short-lived JWT access token and long-lived opaque refresh token, both stored in **HttpOnly cookies**
- **Refresh token rotation**: every refresh consumes the old token and issues a new one
- Refresh tokens are stored as SHA-256 hashes, never in plain text
- Logout revokes the session, so the access token stops working immediately (not only after expiry)
- Protected route middleware that validates the JWT and checks the session is still active
- **RBAC**: roles, permissions, role-permission assignment, and user-role assignment
- Single protected **superadmin** account, bootstrapped from environment variables on first start
- User management (list with pagination, get, update, delete) guarded by permissions
- PostgreSQL migrations with golang-migrate, embedded in the binary and applied on startup
- Unit tests for every package plus an opt-in database integration test suite
- Browser-based API test frontend (Vite + vanilla JavaScript)

## Architecture

The backend uses a layered architecture. Each feature package (`user`, `rbac`) has its own handler, service, and repository.

```text
HTTP Request
     ↓
Router
     ↓
Middleware (Auth → RequirePermission / RequireSuperadmin)
     ↓
Handler      HTTP parsing, validation, status codes, cookies
     ↓
Service      Business logic
     ↓
Repository   SQL queries
     ↓
PostgreSQL
```

### Startup sequence (`main.go`)

1. Load and validate configuration.
2. Enable Gin release mode when `APP_ENV=production`.
3. Run database migrations.
4. Connect to PostgreSQL.
5. Seed the initial superadmin if none exists.
6. Create the JWT service, repositories, services, and handlers.
7. Build the router and start the HTTP server.

## Authentication Design

### Sessions, access tokens, and refresh tokens

Every login creates a row in `sessions`. The two tokens are tied to that session:

| | Access token | Refresh token |
|---|---|---|
| Format | JWT (HS256) | Random 32-byte opaque string |
| Contains | user ID (`sub`), session ID (`jti`), `iat`, `exp` | Nothing, it is only a lookup key |
| Cookie name | `access_token` | `refresh_token` |
| Cookie path | `/` | `/api/v1/auth` (sent only to auth endpoints) |
| Default lifetime | 15 minutes | 7 days |
| Stored in database | No | SHA-256 hash only |

Both cookies are `HttpOnly` and `SameSite=Lax`. The `Secure` flag is enabled when `APP_ENV=production`.

### Login

```text
POST /api/v1/auth/login
        ↓
Find user by email → compare bcrypt hash
        ↓
Create session + refresh token (one transaction)
        ↓
Issue access token bound to the session
        ↓
Set access_token and refresh_token cookies
```

Wrong email and wrong password return the same `401` message to avoid revealing which accounts exist.

### Authenticated request

```text
Request with access_token cookie
        ↓
Validate JWT signature, algorithm, and expiry
        ↓
Check the session is active (not revoked, not expired)
        ↓
Store user ID and session ID in the Gin context
        ↓
Handler
```

Because the session is checked on every request, logging out takes effect immediately even though the JWT itself has not expired yet.

### Refresh token rotation

```text
POST /api/v1/auth/refresh (refresh_token cookie)
        ↓
Look up token hash → lock the session
        ↓
Consume the old refresh token (single use)
        ↓
Extend the session
        ↓
Issue a new access token and a new refresh token
```

All steps run in one database transaction. A refresh token that was already used, expired, or belongs to a revoked session returns `401` and clears both cookies.

### Logout

`POST /api/v1/auth/logout` revokes the current session and deletes its refresh tokens, then clears both cookies.

## Authorization (RBAC)

Access control is stored in the database:

```text
users ──► roles ◄──► permissions
          (via role_permissions)
```

- Each user has exactly one role.
- A role has any number of permissions.
- Permission names use a dotted lowercase format such as `users.read`.
- Role names match `^[a-z0-9][a-z0-9_-]{0,49}$`.

### Built-in rules

- Migrations create two system roles: `user` (default for new registrations) and `superadmin`.
- The system roles `user` and `superadmin` cannot be created, renamed, or deleted through the API.
- There is exactly one superadmin, enforced by a unique partial index on `users.is_superadmin`.
- The superadmin account cannot be updated, deleted, or have its role changed through the API.
- The `superadmin` role cannot be assigned to other users.
- A role that is still assigned to users cannot be deleted, and a permission that is still assigned to roles cannot be deleted.
- The superadmin passes every permission check.

### Permissions used by the API

| Permission | Protects |
|---|---|
| `users.read` | `GET /users`, `GET /users/:id` |
| `users.update` | `PUT /users/:id` |
| `users.delete` | `DELETE /users/:id` |

> The migration does **not** seed these permissions. After the first login as superadmin, create them with `POST /api/v1/permissions` and attach them to a role with `PUT /api/v1/roles/:id/permissions`. Until then, only the superadmin can use the `/users` endpoints.

Roles, permissions, and role assignment (`/roles`, `/permissions`, `PUT /users/:id/role`) are superadmin only.

## Getting Started

### Prerequisites

- Go 1.26 or newer
- PostgreSQL
- Node.js (only for the test frontend)

### 1. Clone the repository

```bash
git clone https://github.com/aslamabdika18/go-auth-jwt.git
cd go-auth-jwt
```

### 2. Create the environment file

```bash
cp .env.example .env
```

Update `.env` for your local setup (see [Environment Variables](#environment-variables)). The three `INITIAL_ADMIN_*` values are required on the first run.

### 3. Create the database

Make sure PostgreSQL is running and the database named in `DB_NAME` exists. Migrations run automatically on startup, so no manual migration step is needed.

```bash
createdb go_auth_jwt
```

### 4. Install dependencies

```bash
go mod download
```

### 5. Run the application

```bash
go run .
```

Or with live reload using [Air](https://github.com/air-verse/air):

```bash
air
```

On the first start the application applies all migrations and creates the superadmin from the `INITIAL_ADMIN_*` values. Check the server with:

```bash
curl http://localhost:8080/health
```

## Environment Variables

```env
APP_NAME=go-auth-jwt
APP_ENV=development
APP_PORT=8080

DB_HOST=localhost
DB_PORT=5432
DB_NAME=go_auth_jwt
DB_USER=postgres
DB_PASSWORD=your_database_password
DB_SSLMODE=disable

JWT_SECRET=replace_with_a_long_random_secret
JWT_ACCESS_TOKEN_TTL=15
JWT_REFRESH_TOKEN_TTL=10080

INITIAL_ADMIN_NAME=
INITIAL_ADMIN_EMAIL=
INITIAL_ADMIN_PASSWORD=
```

| Variable | Description |
|---|---|
| `APP_ENV` | Set to `production` to enable Gin release mode and `Secure` cookies |
| `JWT_ACCESS_TOKEN_TTL` | Access token lifetime in **minutes** (must be > 0) |
| `JWT_REFRESH_TOKEN_TTL` | Refresh token and session lifetime in **minutes** (must be > 0, `10080` = 7 days) |
| `INITIAL_ADMIN_NAME` | Superadmin name, 3 to 100 bytes |
| `INITIAL_ADMIN_EMAIL` | Superadmin email |
| `INITIAL_ADMIN_PASSWORD` | Superadmin password, 12 to 72 bytes |

All variables except the `INITIAL_ADMIN_*` group are required, and the app refuses to start if one is missing or invalid. The `INITIAL_ADMIN_*` values must be all set or all empty, and they are only used while no superadmin exists. Once a superadmin exists they are ignored and can be removed from `.env`.

## API Endpoints

Base path: `/api/v1`. Authenticated endpoints read the `access_token` cookie, so clients must send cookies (for example `credentials: "include"` in `fetch`, or a cookie jar in Postman).

### System

| Method | Endpoint | Access | Description |
|---|---|---|---|
| GET | `/health` | Public | Health check |

### Authentication

| Method | Endpoint | Access | Description |
|---|---|---|---|
| POST | `/auth/register` | Public | Register a new user with the `user` role |
| POST | `/auth/login` | Public | Login and set `access_token` and `refresh_token` cookies |
| POST | `/auth/refresh` | Refresh cookie | Rotate the refresh token and issue a new access token |
| POST | `/auth/logout` | Authenticated | Revoke the current session and clear cookies |
| GET | `/auth/me` | Authenticated | Get the current user |

### Users

| Method | Endpoint | Access | Description |
|---|---|---|---|
| GET | `/users?page=1&page_size=20` | `users.read` | List users (`page_size` 1 to 100) |
| GET | `/users/:id` | `users.read` | Get a user by ID |
| PUT | `/users/:id` | `users.update` | Update a user's name and email |
| DELETE | `/users/:id` | `users.delete` | Delete a user |
| PUT | `/users/:id/role` | Superadmin | Assign a role to a user |

### Roles

| Method | Endpoint | Access | Description |
|---|---|---|---|
| GET | `/roles` | Superadmin | List roles |
| GET | `/roles/:id` | Superadmin | Get a role with its permission IDs |
| POST | `/roles` | Superadmin | Create a role |
| PUT | `/roles/:id` | Superadmin | Update a role |
| DELETE | `/roles/:id` | Superadmin | Delete a role |
| PUT | `/roles/:id/permissions` | Superadmin | Replace the role's permission set |

### Permissions

| Method | Endpoint | Access | Description |
|---|---|---|---|
| GET | `/permissions` | Superadmin | List permissions |
| GET | `/permissions/:id` | Superadmin | Get a permission |
| POST | `/permissions` | Superadmin | Create a permission |
| PUT | `/permissions/:id` | Superadmin | Update a permission |
| DELETE | `/permissions/:id` | Superadmin | Delete a permission |

### Request examples

Register (`name` 3 to 100 characters, `password` 8 to 72 characters):

```json
{
  "name": "Test User",
  "email": "testuser@example.com",
  "password": "PasswordTest123!"
}
```

Login:

```json
{
  "email": "testuser@example.com",
  "password": "PasswordTest123!"
}
```

Create a permission:

```json
{
  "name": "users.read",
  "description": "Read users"
}
```

Set role permissions (an empty array removes all permissions):

```json
{
  "permission_ids": [1, 2, 3]
}
```

Assign a role to a user:

```json
{
  "role_id": 3
}
```

### Error responses

Errors are returned as JSON:

```json
{ "error": "message" }
```

Validation errors include the failing fields:

```json
{
  "error": "validation failed",
  "fields": { "email": "must be a valid email address" }
}
```

| Status | Meaning |
|---|---|
| 400 | Invalid body, invalid ID, or invalid pagination |
| 401 | Missing, invalid, expired, or revoked credentials |
| 403 | Authenticated but missing permission or not superadmin |
| 404 | User, role, or permission not found |
| 409 | Duplicate name or email, resource still in use, or protected superadmin/system role |
| 500 | Unexpected server error |

## Database Schema

| Table | Purpose |
|---|---|
| `users` | Accounts: name, unique email, bcrypt hash, `role_id`, `is_superadmin` |
| `roles` | Role name, description, `is_superadmin` flag |
| `permissions` | Permission name and description |
| `role_permissions` | Many-to-many link between roles and permissions |
| `sessions` | Login sessions with `expires_at` and `revoked_at` |
| `refresh_tokens` | Hashed refresh tokens linked to a user and a session |

Migrations live in `internal/database/migrations/` as `*.up.sql` and `*.down.sql` pairs and are embedded into the binary with `go:embed`.


## API Test Frontend

The `frontend/` folder contains a small Vite app for trying every endpoint without Postman. It includes presets for all 22 routes, an editable JSON body, an input for `:id` paths, and a response panel showing status, duration, size, and body. Requests are sent with cookies, and the Vite dev server proxies `/api` and `/health` to the backend, so no CORS setup is needed.

```bash
cd frontend
npm install
npm run dev
```

Then open `http://127.0.0.1:5173`. The backend target defaults to `http://localhost:8080`. To change it, set `API_TARGET` in `frontend/.env` and restart Vite.

This frontend is a local development tool only. It has no authentication of its own and should not be deployed. See `frontend/README.md` for more details.

## Suggested Manual Test Flow

```text
Register
   ↓
Login
   ↓
GET /auth/me → 200
   ↓
POST /auth/refresh → 200 (new cookies)
   ↓
POST /auth/logout
   ↓
GET /auth/me → 401 (session revoked)
```

To test RBAC, login as the superadmin, create `users.read`, create a role, attach the permission, assign the role to a normal user, then login as that user and call `GET /users`.

## Security Notes

- Use a long random `JWT_SECRET` and keep `.env` out of version control.
- Run behind HTTPS and set `APP_ENV=production` so cookies get the `Secure` flag.
- Passwords are limited to 72 bytes because of the bcrypt input limit.
- Access tokens are short-lived, and refresh tokens are single-use with rotation.
- The API has no rate limiting or login throttling yet. Add them before exposing the service publicly.
